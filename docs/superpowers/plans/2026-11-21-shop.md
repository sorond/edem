# Shop Supply Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a curator shop tab and admin catalogue/order queue where orders reserve treasury funds, approve decrements stock, and cancel/reject/rollback refund money.

**Architecture:** Server-authoritative Supabase RPCs own catalogue, orders, stock, and treasury movements; the static frontend only renders views and sends intents. Pure client helpers handle totals/validation/status copy; DOM modules mount the curator tab and admin blocks using existing CSS classes plus a small set of shop classes.

**Tech Stack:** Static ES modules, Vitest, Supabase Postgres/RLS/PL/pgSQL, SQL test script, GitHub Pages.

**Spec:** `docs/superpowers/specs/2026-11-21-shop-design.md`

## Global Constraints

- UI language: Russian only.
- Palette: `#0a0a0a / #e6e6e6 / #8a8a8a / #5a5a5a`; no green/red/yellow, no glow. Status uses inversion and prefixes `[OK]`, `[!]`, `[ERR]`, `[X]`, `[↩]`.
- One shared curator login. Display author as literal `КУРАТОР`; store `auth.uid()` only for audit.
- Currency: integer game rubles from `public.treasury`. `price >= 0`, `stock >= 0`, quantity integer `> 0`.
- No sound and no toast for shop actions. Feedback is text in the UI.
- No per-order quantity cap except stock and treasury balance.
- Shop actions and stock changes must go through `security definer` RPCs with `search_path = public`; never trust client totals.
- Reserve at submit is a plain treasury decrement, no separate ledger. Approve performs no additional money movement.
- Refunds ignore tax and `treasury_cap`; `credit_treasury` must not be reused for refunds.
- After approval the order composition is immutable. Only `new` orders can be cancelled/edited/reviewed; only `approved` can be rolled back.
- Keep existing economy, auth, data flow, and `prefers-reduced-motion` behavior unchanged.
- Do not put `service_role`, DB password, `SUPABASE_DATABASE_URL`, or `DAILY_PAYOUT_SECRET` into code, tests, or chat.

## Review Focus

- Insufficient treasury at submit: `shop_create_order` must fail with `[ERR]` and create no order; pinned by SQL test T2 in Task 3.
- Insufficient stock or disabled item at approve: order stays `new`, admin sees `[ERR]`, no refund; pinned by SQL test T5 in Task 3.
- Double approve/reject/rollback: second call fails, balance/stock change once; pinned by SQL test T6 in Task 3.
- Curator RLS: curator sees only active items and own orders, cannot call admin RPCs; pinned by SQL test T7 in Task 3.
- History money visibility: `Магазин` filter includes `shop_*` treasury actions and shows amount; pinned by tests in Task 7.

### Task 3: Shop RPC lifecycle

**Files:**
- Modify: `supabase/migrations/004_shop.sql` (append RPC section)

**Interfaces:**
- Consumes: tables and RLS from Task 2.
- Produces RPCs:
  - `shop_get_catalog() -> jsonb`
  - `shop_get_orders() -> jsonb`
  - `shop_create_item(p_name text, p_icon text, p_category text, p_stock integer, p_price bigint) -> jsonb`
  - `shop_update_item(p_id uuid, p_name text, p_icon text, p_category text, p_stock integer, p_price bigint) -> jsonb`
  - `shop_set_item_active(p_id uuid, p_active boolean) -> void`
  - `shop_create_order(p_items jsonb) -> jsonb`, `p_items = [{"itemId":"uuid","quantity":2}]`
  - `shop_cancel_order(p_order_id uuid) -> void`
  - `shop_edit_order(p_order_id uuid, p_items jsonb) -> void`
  - `shop_review_order(p_order_id uuid, p_approve boolean) -> void`
  - `shop_rollback_order(p_order_id uuid) -> void`

**JSON contract (pin exactly — views in Tasks 5–6 consume these keys):**

- `shop_get_catalog()` returns an array of `{ id, name, icon, category, stock, price, active }`. Curator rows are `active = true` only; admin rows include inactive ones. Order by `category, name`.
- `shop_get_orders()` returns an array of `{ id, total, status, created_at, reviewed_at, items }`, newest first (`created_at desc`). Curator sees only own orders; admin sees all. Each `items` entry is `{ nameSnapshot, iconSnapshot, unitPrice, quantity, lineTotal }` in creation order. Author is never returned — UI shows literal `КУРАТОР`.
- `p_items` for both `shop_create_order` and `shop_edit_order` is `[{ "itemId": "uuid", "quantity": 2 }]` (camelCase key `itemId`).
- Internal helpers `debit_treasury` / `refund_treasury` write `public.transactions` with types `shop_reserve`, `shop_adjust`, `shop_refund` and never call `credit_treasury`.

- T2: treasury 50, order total 100 → RPC raises, treasury unchanged, no order.
- T3: `shop_edit_order` from 2 to 3 items at price 100 lowers treasury by another 100; from 3 to 1 adds 200 via `shop_adjust`.
- T4: `shop_review_order(..., false)` and `shop_cancel_order` each restore full total via `shop_refund` and leave stock unchanged.
- T5: admin lowers stock after order creation; approve raises, order stays `new`, no refund, stock unchanged.
- T6: approve once decrements stock; second approve raises; rollback restores stock and refunds; second rollback raises.
- T7: curator calling `shop_create_item` raises; curator `shop_get_catalog` omits inactive item; curator `shop_get_orders` omits admin's order.
