# Магазин / обеспечение ЭДЕМ — дизайн

Статус: черновик на согласование. Реализация не начиналась.

## Зачем

Куратору нужен способ собирать заявку на обеспечение из заранее заданных админом товаров. Сейчас раздел «Задания» закрывает работу с рапортами, но не закрывает выдачу имущества: куратор видит каталог, собирает позиции, оформляет заказ, админ принимает решение. Заказ должен быть не просто записью: одобрение списывает остатки товаров и деньги из общей казны, откат возвращает и то, и другое.

## Цели

- Куратор на главной видит вкладки `[ЗАДАНИЯ] [МАГАЗИН]`; магазин — не отдельная пустая страница.
- Вкладка «МАГАЗИН» показывает список товаров таблицей: иконка, название, категория, остаток, цена, количество, корзина.
- Куратор может изменить количество, оформить заказ, отменить свой заказ со статусом `new`, видеть «МОИ ЗАКАЗЫ» с текущими статусами.
- Админ может создавать/редактировать товары, видеть очередь заказов, менять состав заказа до одобрения, одобрять, отклонять, откатывать одобренный заказ.
- Все денежные движения и остатки меняются только серверными RPC. Клиент только отправляет намерения.
- Деньги приходят из общей казны (`public.treasury`, баланс в игровых рублях). Цена задаётся админом на товар, целое число, за 1 штуку.

## Не цели / антицели

- Не делать личный баланс куратора. Автор заказа в UI — константа `КУРАТОР`; в БД хранится `auth.uid()` только для аудита.
- Не делать реальные платежи, цены в валюте вне игровой казны, налоги на покупки.
- Не добавлять звук и тосты для магазина. Статусы отображаются текстом в UI.
- Не делать жёсткий лимит на количество в заказе, кроме остатка товара и доступных денег в казне.
- Не удалять товары и заказы физически: товары выключаются, заказы сохраняют историю.
- Не трогать экономику заданий, налогов, выплат и daily payout.

## Решения пользователя

1. Размещение: вкладка на главной, выбран вариант C из набросков.
2. Вид каталога: список/таблица, не плитка.
3. Товары задаёт админ; иконка — один символ; категория — свободный текст.
4. Товары с остатком 0 показываются куратору недоступными `[НЕТ]`, не скрываются.
5. Ограничение количества — только остаток.
6. Оплата есть: цена за штуку хранится в товаре, админ редактирует её при создании/изменении товара.
7. Деньги берутся из общей казны.
8. При оформлении деньги резервируются (списываются с казны), при одобрении резерв подтверждается дополнительного списания нет.
9. При нехватке денег оформление блокируется.
10. Отмена куратором, отклонение админом и откат после одобрения возвращают деньги.
11. Админ может менять состав заказа до одобрения; сумма и резерв пересчитываются.
12. После одобрения состав заказа не меняется.
13. В заказе хранится цена на момент оформления; смена цены в каталоге не переписывает старые заказы.
14. Сумма показывается в админке и в «МОИ ЗАКАЗЫ»; списания и возвраты попадают в «ИСТОРИЮ».
15. Заказы хранятся всегда, без удаления, новыми сверху.
16. `prefers-reduced-motion` и ч/б CRT-стиль сохраняются без изменений.

## Решения builders (приняты здесь, пользователем не обсуждались)

- Проверка остатка делается и при оформлении, и при одобрении: админ мог уменьшить остаток после подачи заявки.
- При редактировании заказа админом новые/изменённые позиции получают текущую цену из каталога; `unit_price` в `shop_order_items` обновляется.
- Отклонение не трогает остаток, потому что остаток списывается только при одобрении.
- Откат возвращает остаток по позициям заказа и деньги в казну.
- Товар можно только выключить (`active = false`), не удалять.
- Куратор видит только активные товары; админ видит все, включая выключенные.
- На мобильных таблица каталога прокручивается по горизонтали, без перестроения в карточки.
- В админке добавляются два новых блока: «МАГАЗИН · ЗАКАЗЫ» и «МАГАЗИН · ТОВАРЫ», без верхнего переключателя.
- В журнале истории добавляется фильтр «Магазин» и русские подписи действий/сущностей. Фильтр захватывает `entity in ('shop_item','shop_order')` **или** `action like 'shop_%'`, чтобы денежные движения магазина не исчезали.
- Для магазина добавляются внутренние помощники `debit_treasury` / `refund_treasury` вместо переиспользования `credit_treasury`: резерв не является доходом, возврат не облагается налогом и не ограничивается `treasury_cap`. Все движения пишутся в `transactions` с балансом после операции.
- В «ИСТОРИИ» для действий магазина показывается отдельной строкой `СУММА: ...` из `audit_log.details->>'total'`, потому что сейчас рендер истории не показывает `details`.

## Модель данных

Новая миграция `supabase/migrations/004_shop.sql`.

### `public.shop_items`

- `id uuid primary key default gen_random_uuid()`
- `name text not null`
- `icon text not null check (char_length(icon) = 1)`
- `category text not null`
- `stock integer not null check (stock >= 0)`
- `price bigint not null check (price >= 0)`
- `active boolean not null default true`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Индекс по `(active, category, name)`.

### `public.shop_orders`

- `id uuid primary key default gen_random_uuid()`
- `curator uuid not null references auth.users`
- `status text not null check (status in ('new', 'approved', 'rejected', 'cancelled', 'rolled_back'))`
- `total bigint not null check (total >= 0)`
- `created_by uuid references auth.users`
- `reviewed_by uuid references auth.users`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- `reviewed_at timestamptz`

Индекс по `(status, created_at desc)`.

### `public.shop_order_items`

- `id uuid primary key default gen_random_uuid()`
- `order_id uuid not null references public.shop_orders on delete cascade`
- `item_id uuid not null references public.shop_items`
- `name_snapshot text not null`
- `icon_snapshot text not null`
- `unit_price bigint not null check (unit_price >= 0)`
- `quantity integer not null check (quantity > 0)`
- `line_total bigint not null check (line_total >= 0)`

Индекс по `order_id`. Снимок названия/иконки/цены сохраняется, чтобы история заказа не менялась при редактировании каталога.

### RLS

- `shop_items`: чтение `active or public.is_admin()`; запись только через RPC.
- `shop_orders`: куратор видит только свои строки, админ — все; запись только через RPC.
- `shop_order_items`: чтение через связь с видимым заказом; запись только через RPC.
- Все изменения казны идут через существующие `security definer` RPC с `search_path = public`.

## RPC и переходы

Все RPC проверяют роль через `require_curator()` / `require_admin()` внутри транзакции, блокируют строку заказа/товара `for update`, пишут `audit_log` и при необходимости `transactions`.

| RPC | Кто | Статус | Казна | Остаток |
| --- | --- | --- | --- | --- |
| `shop_create_item`, `shop_update_item`, `shop_set_item_active` | admin | — | — | редактирует поле товара |
| `shop_create_order(p_items jsonb)` | curator | `new` | `-total`, тип `shop_reserve` | проверка, без списания |
| `shop_cancel_order(p_order_id uuid)` | curator, только свой `new` | `cancelled` | `+total`, тип `shop_refund` | без изменений |
| `shop_edit_order(p_order_id uuid, p_items jsonb)` | admin, только `new` | остаётся `new` | дельта, тип `shop_adjust`; при минусе проверка средств | проверка, без списания |
| `shop_review_order(p_order_id uuid, p_approve boolean)` | admin, только `new` | `approved` или `rejected` | при reject `+total`, тип `shop_refund`; при approve без записи | при approve `-quantity` по каждой позиции, при reject без изменений |
| `shop_rollback_order(p_order_id uuid)` | admin, только `approved` | `rolled_back` | `+total`, тип `shop_refund` | `+quantity` по каждой позиции |

Повторное одобрение/отклонение/откат не должно два менять статус: проверка статуса внутри транзакции.

Типы записей `audit_log`: `shop_create_item`, `shop_update_item`, `shop_set_item_active`, `shop_create_order`, `shop_cancel_order`, `shop_edit_order`, `shop_approve_order`, `shop_reject_order`, `shop_rollback_order`. Сущности: `shop_item`, `shop_order`, `treasury`.

Подписи в «ИСТОРИИ»: `ЗАКАЗ МАГАЗИНА`, `ОТМЕНА ЗАКАЗА`, `РЕДАКТИРОВАНИЕ ЗАКАЗА`, `ОДОБРЕНИЕ ЗАКАЗА`, `ОТКЛОНЕНИЕ ЗАКАЗА`, `ОТКАТ ЗАКАЗА`, `СОЗДАНИЕ ТОВАРА`, `ИЗМЕНЕНИЕ ТОВАРА`.

## UI

### Куратор, главная

- В `renderHome` добавляются вкладки `[ЗАДАНИЯ] [МАГАЗИН]`, по умолчанию активны задания.
- Вкладка заданий остаётся текущей: казна, еженедельные, срочные.
- Вкладка магазина:
  - таблица товаров с колонками `ТОВАР / КАТЕГОРИЯ / СКЛАД / ЦЕНА / КОЛ-ВО`;
  - иконка — один символ перед названием;
  - счётчик `[-] N [+]` с максимумом по остатку; при остатке 0 — `[НЕТ]` и счётчик недоступен;
  - строка корзины: количество позиций, сумма, кнопка `[ОФОРМИТЬ ЗАКАЗ]`;
  - блок «МОИ ЗАКАЗЫ»: номер, дата, состав, сумма, статус с префиксом; у `new` — кнопка `[ОТМЕНИТЬ]`.
- Статусы: `[!] НОВЫЙ`, `[OK] ОДОБРЕН`, `[ERR] ОТВЕРГНУТ`, `[X] ОТМЕНЁН`, `[↩] ОТКАТАН`. Инверсия вместо цвета.

### Админка

- Блок «МАГАЗИН · ЗАКАЗЫ»: таблица заявок с номером/датой, составом, суммой, статусом; у `new` — `[ОДОБРИТЬ]`, `[ОТВЕРГНУТЬ]`, `[РЕДАКТИРОВАТЬ]`; у `approved` — `[ОТКАТИТЬ]`.
- Редактирование состава заказа до одобрения: изменение количеств и добавление/удаление позиций из активных товаров. Кнопка `[СОХРАНИТЬ]` вызывает `shop_edit_order`.
- Блок «МАГАЗИН · ТОВАРЫ»: таблица товаров и форма создания/изменения поля `name`, `icon`, `category`, `stock`, `price`, `active`.
- Все сообщения об ошибках имеют префикс `[ERR]`, без цветного свечения.

### История

- Добавить фильтр «Магазин» (`entity in ('shop_item', 'shop_order')`).
- Добавить подписи действий и сущностей из таблицы выше.
- Суммы списаний/возвратов уже попадают в `transactions`; в истории они видны через `audit_log` с суммой в `details`.

## Проверка

- Vitest: чистые функции `orderTotal`, `canFulfill`, `transitionStatus`, форматирование статусов и сумм.
- SQL-тест `supabase/tests/shop_test.sql`: создание товара, заказ, нехватка денег, нехватка остатка, edit, approve, reject, cancel, rollback, повторное действие, RLS по ролям.
- `npm test`: зелёный.
- Браузерный QA: логин curator/admin, вкладки, оформление, отмена, редактирование заказа админом, approve/reject/rollback, цифры казны и остатков, история, мобильная ширина, `prefers-reduced-motion`, консоль без ошибок.
- Миграцию применять так же, как `003`: `supabase db query --remote --file supabase/migrations/004_shop.sql --yes`. `supabase db push --remote` в этом проекте не работает.

- Резерв при оформлении — просто уменьшение баланса казны, без отдельного ledger-счёта. Другие операции казны видят уже уменьшенный баланс; одобрение деньги не проверяет и не списывает повторно.
- Если при одобрении товара не хватает или он выключен, заказ остаётся `new`, админ видит `[ERR]`, возврата денег нет; админ правит состав заказа, пересматривает товар или отклоняет заказ вручную.
